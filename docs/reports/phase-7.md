# Phase 7 — API and research export integration

Date: 2026-10-08. `artifacts/results/manifest.json` hashes six validated source-derived products and the compact browser bundle. The browser bundle contains 160 trial metadata records without waveform arrays (302,672 bytes); `signals.json` is loaded only by the Signals route (7,570,745 bytes). The processing evidence in `signals_detail.json` retains full-rate source-derived arrays and is not published as the initial browser payload. Display traces are explicitly anti-aliased to 100 Hz and keep the conditional 500 Hz source-analysis label. Missing physiological or simulation measurements serialize as null rather than a nominal replacement.

The versioned FastAPI surface consists of `/v1/health`, `/v1/meta`, `/v1/predict` and `/v1/optimize`. Process liveness and compatible-artifact readiness are separate fields. The service loads only the trusted, already fitted local artifact on startup; it never trains in a request. Physical inputs and a user-selected signed target are validated with the shared backend Pydantic schema. Prediction uses the same fitted preprocessing/estimator as CLI and direct calls, reports raw and projected coordinates, target-proximity Neuro-Score, studied-support status and weak-model limitations. Optimization has fixed request bounds, a deterministic seed, explicit empty outcomes and the same scoring/validation path. Invalid requests return structured 422 errors; a missing, malformed or incompatible artifact yields live health with `ready=false` and a structured 503 unavailable result. Metadata document shape and every field consumed by public responses (`artifact_version`, `model_status`, `limitations`) are checked before readiness; compatibility hashes are checked against the current source and artifact. CPU prediction/search runs outside the async event loop, and CORS is configured through `PA_CORS_ORIGINS`.

`pa openapi` regenerates both `artifacts/results/openapi.json` and `room-input.schema.json`. The frontend `api:check` command regenerates client types from that OpenAPI and fails on drift. Backend tests cover synthetic direct/CLI/API parity, actual artifact reload/direct/CLI/API parity, incompatible artifact states, geometry/target/request-limit errors and optimization behavior. Frontend browser tests cover static pages with the API offline and the simulator's offline/unavailable states. After the final source-hash rebuild, a **fresh** isolated production-dependency environment (`uv sync --frozen --no-dev`) started the API and returned `/v1/health` with `ready=true`, `model_status=not_better_than_baseline` and `reason=null`. The hash-staged production frontend build passed, and a single-worker Chromium run against that fresh process passed all 26 tests, including real prediction and optimization. After the final metadata loader change, the regenerated artifact loaded in a fresh process, focused malformed-metadata API regressions and the full backend suite passed, and the clean-clone site/browser tests passed. An earlier long-lived process response was deliberately not accepted as evidence for the final artifact.

The artifact is a weak experimental demonstrator (`not_better_than_baseline`) whose held-out-room MAE exceeded the median baseline. The API's 200 response and score are mathematical computation states, not scientific validation of an emotion detector or design recommendation.
